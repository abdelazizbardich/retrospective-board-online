# DAKI Retrospective: Drop, Add, Keep, Improve Explained

Some retrospective formats are too gentle. When a team knows something is not working but keeps writing it in the "Less" column sprint after sprint without change, they need sharper language. The DAKI retrospective provides exactly that.

DAKI stands for **Drop, Add, Keep, Improve**. Four columns. Four clear directives. Drop what is not serving the team. Add what is missing. Keep what works. Improve what is almost right but needs refinement.

This format pushes teams toward decisive action. It works best with mature teams that have psychological safety and are ready to make hard choices about their process.

## What Is the DAKI Retrospective?

The DAKI retrospective is a four-column Agile reflection format:

| Column | Directive | Question | Action Type |
|--------|-----------|----------|-------------|
| **Drop** | Eliminate | What should we stop doing entirely? | Remove |
| **Add** | Introduce | What should we start doing? | Create |
| **Keep** | Preserve | What is working that we must not lose? | Maintain |
| **Improve** | Refine | What is okay but could be better? | Iterate |

Each column demands a different kind of commitment. Drop requires courage — admitting something failed. Add requires initiative. Keep requires discipline to protect what works under pressure. Improve requires honest assessment of mediocrity.

## When to Use DAKI

DAKI is not for every team or every sprint. Use it when:

- **The team has retrospective experience** and finds gentler formats too vague
- **Recurring problems need a Drop decision**, not another "Less" note
- **Process debt has accumulated** — too many rituals, tools, or habits that no longer serve
- **You want sharper action items** with clear verbs: drop, add, keep, improve
- **Mid-project or quarterly reviews** where bigger changes are on the table

Avoid DAKI for:

- First retrospectives — use [Start Stop Continue](https://sprintsplans.com/blog/start-stop-continue-retrospective-template) instead
- Teams still building [psychological safety](https://sprintsplans.com/blog/psychological-safety-remote-teams)
- Sprints where emotions need processing — try [Mad Sad Glad](https://sprintsplans.com/blog/mad-sad-glad-retrospective)

## How to Facilitate a DAKI Retrospective

Plan 60–75 minutes. Structure the session using our [60-minute retrospective agenda](https://sprintsplans.com/blog/facilitate-retrospective-60-minute-agenda) as a foundation.

### Step 1: Set the Stage (5 minutes)

Explain DAKI and emphasize that "Drop" means genuinely stopping something — not just reducing it. This is the format's defining feature. Teams uncomfortable with directness may need reassurance that Drop targets practices and processes, not people.

Establish ground rules. Reinforce the retrospective prime directive.

### Step 2: Individual Brainstorming (10 minutes)

Display four columns:

```
┌─────────┬─────────┬─────────┬──────────┐
│  DROP   │   ADD   │  KEEP   │ IMPROVE  │
│         │         │         │          │
└─────────┴─────────┴─────────┴──────────┘
```

Ask team members to write at least one card per column. Prompts:

- **Drop:** What practice, meeting, or habit is wasting our time or causing harm?
- **Add:** What is missing that would make a real difference?
- **Keep:** What must we protect even when things get busy?
- **Improve:** What is fine but not great — what would make it better?

Silent writing first. Anonymous input helps when Drop items might feel confrontational.

### Step 3: Share and Cluster (15 minutes)

Share column by column. Start with **Keep** to establish psychological safety before Drop items surface.

Cluster themes. Name patterns. The facilitator should note when Drop and Improve items relate to the same practice — "weekly status email" might appear in Drop while "stakeholder updates" appears in Improve, suggesting the communication need is real but the format is wrong.

### Step 4: Discuss and Decide (25 minutes)

DAKI retrospectives require more decision-making than some formats. The team should leave with clarity on what to drop, not just a list of candidates.

**For Drop items:**
- Is there consensus this should end?
- What will replace the function it served, if anything?
- Who communicates the change to affected parties?

**For Add items:**
- Is this within the team's control?
- What is the smallest version we can try next sprint?

**For Keep items:**
- How do we protect these under pressure?
- Should any Keep items be documented in team working agreements?

**For Improve items:**
- What specifically would "improved" look like?
- Who owns the improvement experiment?

Use dot voting or anonymous voting to prioritize. Tools like [SprintsPlans](https://sprintsplans.com) let teams vote anonymously on Drop and Add proposals, reducing social pressure when decisions are contentious.

### Step 5: Action Items and Close (10 minutes)

DAKI naturally produces action items:

| Column | Typical Action |
|--------|---------------|
| Drop | Announce the change, remove from calendar, update docs |
| Add | Pilot the new practice for one sprint |
| Keep | Document in team agreement, review monthly |
| Improve | Define success criteria, assign owner, revisit next retro |

Limit to one Drop, one Add, and one Improve per sprint. Too many changes at once undermine follow-through. [Turn retrospective feedback into action items](https://sprintsplans.com/blog/turn-retrospective-feedback-into-action-items) with clear owners and check-in dates.

## DAKI Retrospective Examples

### Example 1: Product Development Team

**Drop:**
- Weekly all-hands status meeting that duplicates async updates
- Mandatory code review for typo-only changes
- End-of-sprint heroics to hit arbitrary deadlines

**Add:**
- Definition of Ready checklist for backlog items
- Automated staging deployment on merge to main
- Pairing rotation schedule

**Keep:**
- Daily standup at 9:30am
- Sprint goal visible on the board
- Friday demo to stakeholders

**Improve:**
- Sprint planning — currently runs 3 hours, target 90 minutes
- Bug triage process — works but response time is inconsistent
- Documentation — exists but is hard to find

**Action items:**
1. Drop the weekly status meeting; replace with async update (Owner: Scrum Master)
2. Add Definition of Ready; pilot next sprint (Owner: Product Owner)
3. Improve sprint planning; timebox each section (Owner: Scrum Master)

### Example 2: Operations Team

**Drop:**
- Manual spreadsheet tracking that duplicates the ticketing system
- Escalation via direct messages instead of the queue
- Post-incident reviews that never produce action items

**Add:**
- Runbook for the three most common incidents
- On-call handoff template
- Monthly cross-team dependency review

**Keep:**
- Blameless incident culture
- 15-minute response SLA for critical alerts
- Weekly team lunch

**Improve:**
- Onboarding documentation — comprehensive but outdated
- Alert noise — too many low-priority notifications
- Knowledge sharing — happens informally but not consistently

## DAKI vs. Similar Formats

| Format | Columns | Tone | Best For |
|--------|---------|------|----------|
| DAKI | Drop, Add, Keep, Improve | Decisive | Mature teams ready for change |
| [KALM](https://sprintsplans.com/blog/kalm-retrospective-template) | Keep, Add, Less, More | Balanced | General-purpose retrospectives |
| [Start Stop Continue](https://sprintsplans.com/blog/start-stop-continue-retrospective-template) | Start, Stop, Continue | Simple | New teams |
| [Starfish](https://sprintsplans.com/blog/starfish-retrospective-template) | Start, Stop, Continue, More, Less | Comprehensive | Teams wanting five dimensions |
| [4Ls](https://sprintsplans.com/blog/4ls-retrospective-template) | Liked, Learned, Lacked, Longed For | Reflective | Learning-focused teams |

DAKI's "Drop" is stronger than "Stop" or "Less." "Improve" adds a dimension that KALM's "More" does not capture — the practice that works but needs refinement, not amplification.

## Facilitation Tips for DAKI

### Make Drop Safe

Dropping a practice can feel like admitting failure. Frame it positively: "We tried this, it served a purpose, and now we have better information." [Accountability without blame](https://sprintsplans.com/blog/accountability-without-blame) is essential.

### Prevent Drop Avoidance

Teams often fill Add, Keep, and Improve while leaving Drop empty. Push gently: "Is there anything we are doing out of habit that no longer adds value?" If Drop stays empty sprint after sprint, question whether the team is being honest.

### Improve Is Not a Parking Lot

Improve items should be specific and actionable. "Improve communication" is too vague. "Improve standup by adding a blocker round" is actionable.

### Follow Through on Drops

Dropping something requires active effort — removing calendar invites, updating documentation, telling stakeholders. Assign a Drop owner just like Add and Improve owners.

### Pair DAKI with Root Cause Analysis

When Drop or Improve items recur, dig deeper with [root cause questions](https://sprintsplans.com/blog/sprint-retrospective-questions-root-causes) before deciding to drop or improve.

## Using DAKI for Quarterly Reviews

DAKI scales beyond sprint retrospectives. For quarterly or project-level reviews:

- Expand the time horizon in your prompts
- Allow more Drop items — quarterly is the right cadence for bigger cuts
- Review Keep items against [team health checks](https://sprintsplans.com/blog/team-health-checks)
- Connect improvements to your [continuous improvement system](https://sprintsplans.com/blog/continuous-improvement-system-for-teams)

## Common Mistakes

### Dropping Without Communication

Stopping a meeting or practice without telling affected people creates confusion. Every Drop needs a communication plan.

### Adding Without Dropping

Teams that only Add accumulate process debt. For every Add, ask: "What can we Drop to make room?"

### Ignoring Keep

In the push to Drop and Improve, teams forget to protect what works. Keep items deserve explicit documentation and periodic review.

### Too Many Drops at Once

Dropping three practices in one sprint destabilizes the team. One Drop per sprint is a good default.

## Frequently Asked Questions

### Is DAKI too harsh for some teams?

It can be. Assess your team's psychological safety before using DAKI. If people hesitate to be direct, start with gentler formats and work toward DAKI over time.

### How is Drop different from Stop?

Semantically similar, but "Drop" implies a firmer commitment to elimination. Teams treat Drop decisions more seriously than Stop items, which often reappear sprint after sprint.

### Can DAKI work for remote teams?

Yes. Digital boards with four columns work well. Anonymous posting is valuable for Drop items. Online tools like SprintsPlans support the full DAKI workflow with voting and action item tracking.

### How often should we use DAKI?

Every three to four sprints, or when the team feels stuck. Using DAKI every sprint may lead to change fatigue. Rotate with formats like [Rose Thorn Bud](https://sprintsplans.com/blog/rose-thorn-bud-retrospective-template) or [Sailboat](https://sprintsplans.com/blog/sailboat-retrospective-guide).

### What if the team cannot agree on what to Drop?

Facilitate a structured discussion. List pros and cons. Vote. If consensus is impossible, run an experiment — drop it for one sprint and evaluate.

## Make Decisive Improvements with DAKI

The DAKI retrospective template gives mature teams a framework for honest, decisive reflection. Drop what holds you back. Add what is missing. Keep what works. Improve what is almost there.

It demands more from facilitators and participants than simpler formats — but it rewards that investment with clearer action and less process debt. If your retrospectives produce the same Less notes without change, DAKI might be the format that finally moves the team forward.

Try it in your next retrospective. Be brave with Drop. Be specific with Improve. Protect your Keeps. And follow through — because a DAKI retrospective without action is just a four-column complaint board.
